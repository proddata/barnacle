# Hermit debug console

This is a separate browser UI for manual queries through Hermit. Start it with `docker compose --profile console up --build` and open `http://localhost:8081`. Compose binds it to loopback; the Hermit image and binary do not contain the UI. The workbench includes a Monaco PostgreSQL editor, a schema and table explorer, grid and JSON results with CSV export, and a request debug panel. Drag the dividers to resize the explorer, results, and debug panels; their sizes are saved locally.

Add, rename, save, and switch connections from the connection bar. Host, database, user, and transport settings are saved in browser local storage. Each connection has its own query tabs and in-memory results. Custom passwords and bearer tokens stay in the current browser tab and must be entered again after a reload. The built-in Compose connection is prefilled with its published development password. Query text and results are not saved between reloads.

`Run query` or `Ctrl/Cmd+Enter` executes the selection, or the statement under the cursor when nothing is selected. `Run all` executes every statement in the active tab in order, stops on the first error, and adds one result tab per statement. The editor recognizes semicolons inside PostgreSQL quotes, comments, and dollar-quoted strings. Each statement uses a separate Neon driver call, so a script does not share a database transaction or session across statements. Use one statement at a time for session-dependent SQL.

The console uses the pinned `@neondatabase/serverless` driver. Its HTTP password and HTTP bearer modes use `neon()`. WebSocket password mode uses `Client`, with pipelined password startup disabled so SCRAM and MD5 challenges can be negotiated. PostgreSQL or PgBouncer normally chooses the password authentication method. For HTTP password tests, the method selector can require SCRAM-SHA-256 or MD5 and fail if the upstream offers another method. WebSocket uses automatic negotiation. An OIDC-gated Hermit requires OAuth for HTTP bearer mode. WebSocket cookie-gated access requires a trusted frontend to set the `hermit_access_token` cookie; typing a bearer token into the HTTP field does not set that cookie.

The host and port in the form are sent as the requested PostgreSQL route. In fixed mode, Hermit ignores that host and uses `HERMIT_PG_ADDR`. To try multiple targets, set `HERMIT_PG_ALLOWED_ADDRS` to their exact `host:port` values and configure TLS certificates trusted by Hermit for each target. The console container only proxies `/sql` and `/v2` to Hermit; it cannot bypass Hermit's allowlist.

For the default Compose database, use host `postgres:5432`, database `hermit`, user `hermit`, and password `hermit_dev_password`. Refresh the explorer to load schemas, tables, and views. Expand a table to see its columns or click ↗ to open and run a 100-row preview. For HTTP calls, the debug panel shows the actual driver request headers in a table and the exact JSON body passed to `fetch`, plus timing and a bounded response preview. The connection string password and bearer token are masked. WebSocket calls show their logical PostgreSQL operation; the driver sends binary protocol frames rather than an HTTP JSON body. SQL, parameters, and result data are visible to the person using the console.

Custom passwords, tokens, query text, and results remain in the browser page for the current session. The default Compose password is included in this development-only console bundle. Requests use HTTP on the local console origin in this setup. Deploy the UI only behind a suitable private HTTPS ingress if it is needed outside local development. For local frontend development, run `npm ci && npm run dev` here while Hermit listens on `127.0.0.1:8080`; Vite proxies `/sql` and `/v2` to Hermit.
