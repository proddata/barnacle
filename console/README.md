# Barnacle debug console

This is a development and debugging UI for manual queries through Barnacle. Do not deploy the console in production. Start it with `docker compose --profile console up --build` and open `http://localhost:8081`. Compose binds it to loopback; the Barnacle image and binary do not contain the UI. The workbench includes a Monaco PostgreSQL editor, a schema and table explorer, grid and JSON results with CSV export, and a request debug panel. Drag the dividers to resize the explorer, results, and debug panels; their sizes are saved locally. The **Metrics** view shows Barnacle's active and total WebSocket connections, active HTTP SQL requests, HTTP SQL counters and duration distribution, and the raw Prometheus response. It refreshes every five seconds. Switching views keeps the workbench and its WebSocket sessions open. Compose enables metrics for local development; set `BARNACLE_METRICS=false` to disable them. The console proxies `/metrics` to Barnacle's separate port `9090`, so keep that port when using this view.

Add, rename, save, and switch connections from the connection bar. Host, database, user, and transport settings are saved in browser local storage. Each connection has its own query tabs and in-memory results. Custom passwords and bearer tokens stay in the current browser tab and must be entered again after a reload. The built-in Compose connection is prefilled with its published development password. Query text and results are not saved between reloads. With WebSocket selected, the connection panel shows the active tab's connection state and **Connect** and **Disconnect** actions. Disconnect closes the tab's session; the next Connect opens a fresh session with cleared PostgreSQL session state. Running SQL also connects automatically when needed.

**Run all** or `Ctrl/Cmd+Enter` runs every statement in the active tab when no text is highlighted. Highlight SQL to change the action to **Run selection**; only the selected text runs. Statements run in order, stop on the first error, and each successful statement gets a result tab. With an HTTP transport selected, the **One transaction** checkbox changes this action to a single non-interactive `sql.transaction()` request: results appear together after completion, and the limit is 100 statements. This choice is saved with the connection profile. Keep explicit `BEGIN`, `COMMIT`, and `ROLLBACK` out of HTTP batches if you want ordinary all-or-nothing transaction behavior. The Examples menu opens a new tab with a delayed transaction, an intentionally failed transaction, or a server information query. For the failed example, Run all stops at division by zero; highlight and run the following statements individually to see the aborted-transaction error, roll back, and verify recovery. The editor recognizes semicolons inside PostgreSQL quotes, comments, and dollar-quoted strings. WebSocket queries in one editor tab share a PostgreSQL session, including across separate runs, so `BEGIN`, subsequent statements, and `COMMIT` work together. Closing the tab or changing its connection settings closes that session. Ordinary HTTP queries remain independent requests.

The console uses the pinned `@neondatabase/serverless` driver. Its HTTP password and HTTP bearer modes use `neon()`. WebSocket password mode uses `Client`, with pipelined password startup disabled so SCRAM and MD5 challenges can be negotiated. PostgreSQL or PgBouncer normally chooses the password authentication method. For HTTP password tests, the method selector can require SCRAM-SHA-256 or MD5 and fail if the upstream offers another method. WebSocket uses automatic negotiation. An OIDC-gated Barnacle requires OAuth for HTTP bearer mode. WebSocket cookie-gated access requires a trusted frontend to set the `barnacle_access_token` cookie; typing a bearer token into the HTTP field does not set that cookie.

The host and port in the form are sent as the requested PostgreSQL route. The local Compose stack accepts external hosts by default (`BARNACLE_PG_ALLOWED_ADDRS=*`). Enter the PostgreSQL host and port from your provider, not a connection URL. Barnacle verifies its TLS certificate against that host; the Compose CA bundle includes system roots and the local development CA. To restrict routing, set `BARNACLE_PG_ALLOWED_ADDRS` to exact `host:port` values (including `postgres:5432` if you also want the local database), or set it to an empty string for fixed mode. The console container proxies `/sql`, `/v2`, and `/metrics` to Barnacle. The workbench uses the Neon driver. Metrics are for the Barnacle instance behind the console, regardless of which database connection is selected in the workbench.

For a hosted PostgreSQL service, copy the host, port, database, and user from its connection information. The port may differ from `5432`. Download its CA certificate, save it as `console/certs/ca.pem`, and restart the stack with:

```sh
BARNACLE_PG_EXTRA_CA_FILE=/console-certs/ca.pem docker compose --profile console up --build -d
```

The extra CA is added to Barnacle's system and local development CAs, so the local database still works. Keep the certificate file in `console/certs/`, which is ignored by Git. If the connection still fails, check the host and port, database, user, and password against the provider's connection information.
To retain the CA setting on later Compose starts, put `BARNACLE_PG_EXTRA_CA_FILE=/console-certs/ca.pem` in a local root `.env` file; `.env` is ignored by Git.

For the default Compose database, use host `postgres:5432`, database `barnacle`, user `barnacle`, and password `barnacle_dev_password`. Refresh the explorer to load schemas, tables, and views. Expand a table to see its columns or click ↗ to open and run a 100-row preview. For HTTP calls, the debug panel shows the actual driver request headers in a table and the exact JSON body passed to `fetch`, plus timing and a bounded response preview. The connection string password and bearer token are masked. WebSocket calls show their logical PostgreSQL operation in the debug panel, and the Activity list labels calls that reuse a connection. The server's startup `ParameterStatus` values and backend process ID appear in a table below the Explorer for the active editor tab's WebSocket session. The cancellation secret is not displayed. The driver sends binary protocol frames rather than an HTTP JSON body. SQL, parameters, and result data are visible to the person using the console.

Custom passwords, tokens, query text, and results remain in the browser page for the current session. The default Compose password is included in this development-only console bundle. Requests use HTTP on the local console origin in this setup. If developers need remote access, use a private HTTPS ingress and keep the console out of production deployments. For local frontend development, run `npm ci && npm run dev` here while Barnacle listens on `127.0.0.1:8080`; Vite proxies `/sql`, `/v2`, and `/metrics` to Barnacle.
